# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

A marketing/blog website for "Goblin's Lair," a Warhammer 40,000 / Age of Sigmar tabletop hobby shop, built with Astro. Output is `'static'` in `astro.config.mjs` (most pages prerender to plain HTML/CSS/JS), but the site now runs the `@astrojs/vercel` adapter so individual routes can opt into on-demand server rendering with `export const prerender = false` — used by the product item page (see Architecture below), which needs to serve hundreds of products without pre-building a file per product. Hosted on Vercel; `npm run build` outputs to `.vercel/output/` (Vercel's format) rather than a plain portable `dist/` now that a server route exists — deploying elsewhere would need a different Astro adapter for that host, or dropping the dynamic product route back to static generation.

## Commands

```
npm install              # install deps
npm run dev               # start local dev server (usually http://localhost:4321)
npm run build             # build for Vercel (outputs to .vercel/output/)
npm run preview           # serve the build locally
npm run sync-products     # pull the live catalog from Loyverse POS into src/content/products/
npm run sync-paint-images # fill missing Paints-category product images from GW's trade resource library
```

`.env` (not committed): `LOYVERSE_ACCESS_TOKEN` (required by both sync scripts), `LOYVERSE_STORE_ID` (optional). `SITE_URL` is read at build time by `astro.config.mjs` for the production domain (sitemap, canonical tags, OG/Twitter meta, JSON-LD) — unset in Vercel's env vars as of this writing, so it currently falls back to a `https://example.com` placeholder baked into the build. Set it once a domain is assigned.

There is no test suite, linter, or type-checker configured in this repo.

## Architecture

- **Pages** (`src/pages/`) are file-based routes: `index.astro`, `about.astro`, `products.astro`, `contact.astro`, `blog/index.astro` (listing), `blog/[slug].astro` (dynamic post route via `getStaticPaths`, prerendered — one HTML file per post), `products/[slug].astro` (dynamic product route, **not** prerendered — renders per-request on Vercel instead of generating hundreds of files), `404.astro` (branded not-found page), `robots.txt.ts` (dynamic endpoint, not a static file, so it can read `Astro.site` for the `Sitemap:` line). Every page wraps its content in `src/layouts/BaseLayout.astro`, which owns the `<head>` (`title`/`description`, canonical link, `og:*`/`twitter:*` meta, LocalBusiness JSON-LD, `image` prop optional), header/nav, mobile menu markup, and footer.
- **Blog content** is an Astro Content Collection: markdown files in `src/content/blog/*.md` validated against the schema in `src/content/config.ts` (`title: string`, `date: date`, `excerpt: string`). Adding a new post is just adding a new `.md` file with that frontmatter — no other files need to change, and a page is generated automatically at `/blog/<file-name>` (slug = filename).
- **Homepage events** are an Astro Content Collection too: markdown files in `src/content/events/*.md`, same three-field schema as blog (`title`, `date`, `excerpt`) — no dedicated event pages, just data consumed by `index.astro`'s EVENTS section. The homepage sorts by date and shows up to four *upcoming* events (soonest first, soonest = featured card); if none are upcoming it falls back to the four most recent past events under a "Recently at the Lair" heading instead of rendering an empty section. Since `index.astro` is prerendered, this list is only as fresh as the last build/deploy — adding an event still requires a commit+push, same as a blog post.
- **Product content** is a `'data'` Content Collection: JSON files in `src/content/products/*.json`, schema in `src/content/config.ts`. These files are **generated**, not hand-authored — `npm run sync-products` (`scripts/sync-products.mjs`) wipes and regenerates them from the Loyverse POS API (catalog, pricing, per-store stock) using `LOYVERSE_ACCESS_TOKEN` (and optional `LOYVERSE_STORE_ID`) from `.env`. Re-run it whenever the shop's catalog/stock should refresh on the site — `products.astro` (the grid) is static and only reflects the last sync until the site rebuilds; `products/[slug].astro` (the item page) reads the same synced JSON but server-renders per request, so it's as fresh as the last sync but doesn't require a rebuild to serve (and now sets a real 404 status via `Astro.response.status = 404` plus branded markup for unknown slugs, instead of an empty response). Loyverse item descriptions arrive as HTML and are stripped to plain text by the sync script (`stripHtml`) before being stored. `npm run sync-paint-images` (`scripts/sync-paint-images.mjs`) is a companion script: fills in missing product images for Paints-category items from GW's public trade resource library, matching by colour name since SKUs don't line up between the two systems. Online checkout/cart is not implemented — product pages are informational only.
- **Product filtering** (`products.astro` + `public/product-filter.js`) is a slide-out drawer, not flat tag pills — the 60+ raw Loyverse categories are grouped server-side into game systems (Warhammer 40,000, Age of Sigmar, The Horus Heresy, Other Games, Hobby & Supplies) with drill-down navigation, plus root-level entries (currently Combat Patrol, Spearhead) for product lines that cut across every faction. Each filter "entry" carries a `categoryMatch` (the real Loyverse category slug, or `*` to ignore category entirely) and optional `namePrefix` (AND constraint, narrows within a category) or `nameContains` (OR constraint, pulls in matches from *other* categories without removing them from their own — e.g. AoS products named "Spearhead: ..." still show under their own faction filter too). See the comments above `FilterEntry` in `products.astro` before changing the matching logic.
- **Contact form** (`contact.astro` + `public/contact-form.js`) intercepts submit, validates client-side, and posts JSON to `/api/contact` — that endpoint does not exist yet (no backend has been chosen), so submissions currently always hit the catch branch, which shows a clear error pointing people at `goblinslairpj@gmail.com` instead of silently losing the message. Swap `CONTACT_ENDPOINT` in `contact-form.js` for a real endpoint (Formspree, a Vercel function, etc.) when one is chosen.
- **SEO**: `@astrojs/sitemap` is configured in `astro.config.mjs`; since `products/[slug].astro` opts out of prerendering, its ~500 routes are invisible to the sitemap integration's normal build-manifest scan, so they're added explicitly via `customPages` (reads the same JSON files `sync-products` writes). `site` in `astro.config.mjs` reads `process.env.SITE_URL`, falling back to a placeholder until a domain exists (see Commands above).
- **No client-side framework or bundler-managed JS.** Interactive behavior (hero slideshow, scroll parallax, mobile menu, product filtering, contact form, scroll-reveal) lives in plain vanilla JS files under `public/` (`hero-slideshow.js`, `parallax.js`, `mobile-menu.js`, `product-filter.js`, `contact-form.js`, `scroll-reveal.js`), each an IIFE, and is wired into pages via `<script src="..." is:inline>` tags rather than Astro component imports. Follow this pattern for new interactive widgets rather than introducing a UI framework.
- **Styling** is a single global stylesheet at `public/style.css`, linked from `BaseLayout.astro`. There are no CSS modules or scoped `<style>` blocks in use.
- **Photography** lives in `src/assets/images/` and goes through Astro's build-time image pipeline (resized, re-encoded to WebP) rather than being served verbatim from `public/`. `src/pages/index.astro` resolves it with an eager `import.meta.glob` over `*.{jpg,jpeg,png}` keyed by basename: `hero-1`–`hero-5` for the slideshow, `reason-1`–`reason-5` for the diamonds in the Reasons section. Dropping a correctly-named file in replaces the CSS gradient placeholder without touching page code; a missing name keeps its gradient. A plain-English version for non-developers is in `HOW-TO.md`. Product photography (Loyverse-hosted, referenced by URL) renders via `background-size:contain` (not `cover`) so box art is never cropped.
