# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

A marketing/blog website for "Goblin's Lair," a Warhammer 40,000 / Age of Sigmar tabletop hobby shop, built with Astro. Output is `'static'` in `astro.config.mjs` (most pages prerender to plain HTML/CSS/JS), but the site now runs the `@astrojs/vercel` adapter so individual routes can opt into on-demand server rendering with `export const prerender = false` — used by the product item page (see Architecture below), which needs to serve hundreds of products without pre-building a file per product. Hosted on Vercel; `npm run build` outputs to `.vercel/output/` (Vercel's format) rather than a plain portable `dist/` now that a server route exists — deploying elsewhere would need a different Astro adapter for that host, or dropping the dynamic product route back to static generation.

## Commands

```
npm install              # install deps
npm run dev               # start local dev server (usually http://localhost:4321)
npm run build             # build for Vercel (outputs to .vercel/output/)
npm run preview           # serve the build locally
npm run sync-products     # pull the live catalog from Loyverse POS into src/content/products/
npm run sync-paint-images # fill missing Paints-category product images from GW's trade resource library
```

`npm run sync-products` also now runs automatically every hour via `.github/workflows/sync-products.yml` (a GitHub Action, `schedule` + manual `workflow_dispatch`), committing any catalog changes back to `main` — that push triggers Vercel's normal git-based deploy. It needs `LOYVERSE_ACCESS_TOKEN` (and optional `LOYVERSE_STORE_ID`) set as GitHub repo secrets (Settings → Secrets and variables → Actions), separate from the same-named `.env` vars used locally. See Architecture below for why per-request stock no longer strictly depends on this running frequently.

`.env` (not committed, see `.env.example`): `LOYVERSE_ACCESS_TOKEN` (required by both sync scripts), `LOYVERSE_STORE_ID` (optional). `SITE_URL` is read at build time by `astro.config.mjs` for the production domain (sitemap, canonical tags, OG/Twitter meta, JSON-LD) — unset in Vercel's env vars as of this writing, so it currently falls back to a `https://example.com` placeholder baked into the build. Set it once a domain is assigned. `DATABASE_URL` (pooled Neon Postgres connection string) is required by the login system and the cart — see Architecture below. `ADMIN_PASSWORD_HASH`, `GITHUB_TOKEN`, `GITHUB_REPO` are required by the `/admin` content panel — see Architecture below.

There is no test suite, linter, or type-checker configured in this repo.

## Architecture

- **Pages** (`src/pages/`) are file-based routes: `index.astro`, `about.astro`, `products.astro`, `contact.astro`, `blog/index.astro` (listing), `blog/[slug].astro` (dynamic post route via `getStaticPaths`, prerendered — one HTML file per post), `products/[slug].astro` (dynamic product route, **not** prerendered — renders per-request on Vercel instead of generating hundreds of files), `404.astro` (branded not-found page), `robots.txt.ts` (dynamic endpoint, not a static file, so it can read `Astro.site` for the `Sitemap:` line). Every page wraps its content in `src/layouts/BaseLayout.astro`, which owns the `<head>` (`title`/`description`, canonical link, `og:*`/`twitter:*` meta, LocalBusiness JSON-LD, `image` prop optional), header/nav, mobile menu markup, and footer.
- **Blog content** is an Astro Content Collection: markdown files in `src/content/blog/*.md` validated against the schema in `src/content.config.ts` (`title: string`, `date: date`, `excerpt: string`). Collections use the Content Layer API (`glob()` loader from `astro/loaders`, not the legacy `type: 'content'`/`type: 'data'` shorthand removed in Astro 6) — entries expose `.id` (the filename, used as the slug) rather than `.slug`, and rendering a post's body is `const { Content } = await render(post)` (imported from `astro:content`) rather than `post.render()`. A page is generated automatically at `/blog/<file-name>` (slug = filename). Files can still be added/edited by hand, but the `/admin` panel (see below) is the normal way to publish now.
- **Homepage events** are an Astro Content Collection too: markdown files in `src/content/events/*.md`, same schema as blog plus one extra field (`title`, `date`, `excerpt`, `image: string | null`) — no dedicated event pages, just data consumed by `index.astro`'s EVENTS section. The homepage sorts by date and shows up to four *upcoming* events (soonest first, soonest = featured card); if none are upcoming it falls back to the four most recent past events under a "Recently at the Lair" heading instead of rendering an empty section. Since `index.astro` is prerendered, this list is only as fresh as the last build/deploy — adding an event (by hand or via `/admin`) still means a commit+push, same as a blog post, and Vercel's resulting deploy (~30–90s) is the only real delay. Unlike blog posts, events have no body/content field to embed an inline image into — instead `image` is a single featured-image URL shown only on the *highlighted* event card (`.events-image` background in the EVENTS section), not the compact list rows. The admin event forms reuse `public/admin-image-upload.js` (same compress-then-upload-to-Blob pipeline as blog), but in a different mode: when the form has no `#body` textarea, the script sets a hidden `#image` input's value and shows a `#admin-image-preview` thumbnail instead of inserting a markdown tag.
- **Product content** is a `'data'`-style Content Collection: JSON files in `src/content/products/*.json`, schema in `src/content.config.ts` (includes each product's Loyverse `variantId`, needed for the live stock lookup below). These files are **generated**, not hand-authored — `npm run sync-products` (`scripts/sync-products.mjs`) wipes and regenerates them from the Loyverse POS API (catalog, pricing, per-store stock) using `LOYVERSE_ACCESS_TOKEN` (and optional `LOYVERSE_STORE_ID`) from `.env`, and also runs hourly via GitHub Action (see Commands above) so name/price/description/new-or-removed products stay current without someone running it by hand. Both `products.astro` (the grid) and `products/[slug].astro` (the item page) are server-rendered (`prerender = false`) and overlay **live** stock from Loyverse on top of that synced snapshot via `src/lib/loyverse-stock.ts` (`getLiveStockMap`/`getLiveStockForVariant`, a direct `/inventory` API call per request, 20s in-memory cache, falls back to the synced snapshot's stock value if the live lookup fails) — so stock reflects an in-store sale on the next page view, not just the last sync; name/price/description/category are still only as fresh as the last sync, which is fine since those don't change per sale. Loyverse item descriptions arrive as HTML and are stripped to plain text by the sync script (`stripHtml`) before being stored. `npm run sync-paint-images` (`scripts/sync-paint-images.mjs`) is a companion script: fills in missing product images for Paints-category items from GW's public trade resource library, matching by colour name since SKUs don't line up between the two systems.
- **Product filtering** (`products.astro` + `public/product-filter.js`) is a slide-out drawer, not flat tag pills — the 60+ raw Loyverse categories are grouped server-side into game systems (Warhammer 40,000, Age of Sigmar, The Horus Heresy, Other Games, Hobby & Supplies) with drill-down navigation, plus root-level entries (currently Combat Patrol, Spearhead) for product lines that cut across every faction. Each filter "entry" carries a `categoryMatch` (the real Loyverse category slug, or `*` to ignore category entirely) and optional `namePrefix` (AND constraint, narrows within a category) or `nameContains` (OR constraint, pulls in matches from *other* categories without removing them from their own — e.g. AoS products named "Spearhead: ..." still show under their own faction filter too). See the comments above `FilterEntry` in `products.astro` before changing the matching logic.
- **Contact form** (`contact.astro` + `public/contact-form.js`) intercepts submit, validates client-side, and posts JSON to `/api/contact` — that endpoint does not exist yet (no backend has been chosen), so submissions currently always hit the catch branch, which shows a clear error pointing people at `goblinslairpj@gmail.com` instead of silently losing the message. Swap `CONTACT_ENDPOINT` in `contact-form.js` for a real endpoint (Formspree, a Vercel function, etc.) when one is chosen.
- **Customer login** is email+password with server-side sessions. `src/lib/load-env.ts` has a manual `.env` parser called by any `src/lib/*` module that reads `process.env` directly (`db.ts`, `loyverse.ts`) — Astro/Vite only bridges `.env` into `import.meta.env`, not the real `process.env`, so plain `process.env.X` is `undefined` in local `astro dev` without this (production is unaffected; Vercel injects real env vars there). `src/lib/db.ts` holds a single `postgres` (porsager/postgres) client reading `DATABASE_URL` (a pooled Neon connection string — no ORM, no migration framework; run `scripts/schema.sql` once by hand against a new database, or `scripts/add-customer-name.sql` to patch an existing one created before the `name` column existed). `src/lib/auth.ts` has the password hashing (`bcryptjs`, cost 12) and DB-backed session helpers — sessions are opaque random tokens stored in a `sessions` table (not JWT), so logout deletes the row and revokes immediately; `getSessionCustomer` falls back to the email's local-part as a display name for accounts created before `name` existed. `src/pages/api/{signup,login,logout,me}.ts` and `src/pages/api/account/{name,password,delete}.ts` are `prerender = false` `APIRoute` endpoints (same shape as `robots.txt.ts`) — the `account/` ones all require a valid session (401 otherwise), and `password`/`delete` re-verify the current password before acting. `src/pages/login.astro` and `signup.astro` are static forms; `public/login-form.js` and `signup-form.js` follow `contact-form.js`'s fetch/catch pattern. `src/lib/rate-limit.ts` (`checkRateLimit(key, maxAttempts, windowMinutes)`) throttles brute-force attempts against `login`, `signup`, and `admin/login` — a fixed-window counter in a `rate_limits` table (`scripts/schema.sql` / one-off `scripts/add-rate-limits-table.sql`) keyed by `${route}:${clientAddress}`, not in-memory state, since Vercel serverless functions don't share memory across instances/regions. Customer login/signup allow 10 attempts per 15 minutes per IP; admin login is stricter at 5, since that single shared password gates GitHub commit and Blob write access for the whole site. `public/nav-auth.js` calls `GET /api/me` on every page load and toggles each `.nav-account` block (one in each of `BaseLayout.astro`'s two separately-hardcoded nav lists) between a plain "Login" pill (`.nav-cta`) and a dropdown trigger showing the customer's name, opening a `.nav-dropdown` with "My Account" / "Logout" — `BaseLayout` itself stays static/prerendered rather than becoming a server route just for nav state.
- **My Account page** (`src/pages/account.astro`, `prerender = false`, redirects to `/login` if there's no session) covers edit name, change password, and self-service account deletion (`public/account-page.js` + the `api/account/*` routes above), plus a read-only membership tier section powered by `src/lib/loyverse.ts`. That lookup links the website account to a Loyverse customer **by email** (`GET /customers?email=`, same auth pattern as `scripts/sync-products.mjs`) and searches the free-text `note` field for the substrings `"level 1"` / `"level 2"` (case-insensitive, `"level 2"` checked first) to determine a 10%/15% discount — there's no separate linking table, so it silently shows "no tier found" if the customer's in-store Loyverse profile has no email or a different one than they signed up with here; that's an expected outcome for a mismatch, not an error.
- **Cart** is account-owned, not browser-owned — deliberately not `localStorage`-only, because a shared/kiosk computer would otherwise hand one customer's cart to the next person who logs in there (this was a real bug, fixed by moving storage server-side). `public/cart.js` is the client engine (`window.GLCart`: `addItem`/`updateQty`/`removeItem`/`clear`/`readCart`), backed by a `carts` table (`customer_id` PK, `items` jsonb — `scripts/schema.sql` / one-off `scripts/add-cart-table.sql` for an existing DB) via `src/pages/api/cart.ts` (`GET`/`PUT`, session-gated like `api/account/*`). `localStorage` is still used, but only as a guest scratchpad (pre-login) or a local mirror of the account's server cart, and is tagged with the owning account's email (`gl-cart-owner`) — `public/nav-auth.js` dispatches a `gl:auth` event (`{loggedIn, email}`) after every `GET /api/me` call, which `cart.js` listens for: logging in pulls the account's server cart down and folds in any local items *not already owned by that account* (so a stale cart left by a different session gets discarded, not merged); logging out (or the local cart's tagged owner not matching whoever's now logged in) clears it. Cart changes push to the server (debounced 400ms) whenever `loggedIn` is true. `public/product-detail.js` (product page) and `public/product-grid-cart.js` (grid quick-add, event-delegated so it survives `product-filter.js`'s show/hide) both cap quantity to the product's POS `stock` — including whatever's already in the cart — and render a disabled "Out of Stock"/"Max in Cart" button rather than hiding the control. `src/pages/cart.astro` (`prerender = false`) is the cart page: renders items via `public/cart-page.js` reading `GLCart`, computes the membership discount server-side (same `getMembershipTier` lookup as the account page) and hands the percentage to the client as a data attribute, and requires sign-in to check out — logged-out visitors get a "Sign In to Checkout" link to `/login?redirect=/cart` instead of the (still-stubbed, no payment gateway) checkout button; `public/login-form.js` reads that `redirect` query param after a successful login and returns the customer there (validated same-site-only, so it can't be used as an open redirect).
- **Admin panel** (`/admin`, gated by a single shared staff password — not a customer account/`is_admin` flag) lets staff publish blog posts and events through a form instead of hand-writing markdown files, while keeping content as git-tracked `.md` files (no database rework, no change to how the public pages read content). `src/lib/admin-auth.ts` mirrors `src/lib/auth.ts`'s session pattern (opaque token in a DB table, `admin_sessions` — `scripts/schema.sql`/`scripts/add-admin-sessions-table.sql`) but checks `bcrypt.compare` against a single `ADMIN_PASSWORD_HASH` env var instead of a customer row, since there's only one admin identity. `src/lib/github-content.ts` wraps GitHub's REST Contents API with plain `fetch` (`GITHUB_TOKEN`, a fine-grained PAT scoped to just this repo with Contents read/write; `GITHUB_REPO`) to list/read/create/update/delete files directly in `src/content/blog/` and `src/content/events/` — so hitting Publish/Save/Delete in the admin panel *is* a real commit to `main`, which triggers the same Vercel deploy the hourly product sync relies on (content goes live in roughly a normal deploy's time, not instantly — a deliberate tradeoff over a live-fetch-per-request approach, which would've added GitHub API latency to every blog/event page view for a gain nobody would notice at this traffic size). `src/lib/markdown.ts` has minimal hand-rolled frontmatter build/parse helpers (no `gray-matter` dependency, matching the codebase's minimal-dependency style) — not a general YAML parser, only handles the flat string fields (`title`/`date`/`excerpt`, plus an optional `image` written only when present so blog posts keep their plain three-line frontmatter) this site's frontmatter ever uses. `src/lib/slug.ts` is the `slugify()` used by the admin routes to turn a title into a filename (a title is only ever slugified once, at creation — editing a post/event keeps its original filename/slug even if the title changes, to avoid the rename/old-file-cleanup case). `src/pages/api/admin/{blog,events}.ts` (GET/POST/PUT/DELETE, all requiring a valid admin session) do the actual reading/writing; `src/pages/admin/{blog,events}/{new,[slug]/edit}.astro` are the forms, `src/pages/admin/index.astro` lists everything live from GitHub (so the admin's own list is never stale, even though the *public* site still lags by a deploy). Both blog posts and events can embed/attach images via a file input wired to `public/admin-image-upload.js`, which downscales/recompresses the file client-side via canvas (max width 1600px, JPEG quality 0.82 — so a typical multi-MB phone photo shrinks to a few hundred KB before staff ever notice a cap) then base64-encodes the result and posts it as JSON (not `multipart/form-data` — Astro's default CSRF check, `security.checkOrigin`, blocks form-content-type POSTs whose Origin header doesn't line up exactly, and every other admin route already sidesteps this the same way) to `src/pages/api/admin/upload.ts` (admin-session-gated like the other admin routes, 3MB cap on the compressed upload — base64 inflates ~33% and Vercel's Node function body limit is 4.5MB) — that route resizes/re-encodes it again server-side with `sharp` (max width 1600px, WebP quality 80, matching the treatment `src/pages/index.astro`'s hero/reason photography gets from Astro's own image pipeline) and uploads it to Vercel Blob storage (`@vercel/blob`, needs `BLOB_READ_WRITE_TOKEN`). Deliberately *not* committed into the repo as a file: git blobs never shrink (even a deleted/replaced image's bytes stay in history), so binary images belong in Blob storage, not GitHub Contents API commits, unlike the blog/event markdown text itself. What happens with the resulting URL differs by form: blog posts have a body textarea, so it inserts a `![](url)` markdown tag at the cursor (image can go anywhere in the post, see below); events have no body field, so it instead sets a hidden `#image` input's value (shown on the homepage's *highlighted* event card only, see below) — `admin-image-upload.js` picks the mode based on which of `#body`/`#image` exists in the form.
- **SEO**: `@astrojs/sitemap` is configured in `astro.config.mjs`; since `products/[slug].astro` opts out of prerendering, its ~500 routes are invisible to the sitemap integration's normal build-manifest scan, so they're added explicitly via `customPages` (reads the same JSON files `sync-products` writes). `site` in `astro.config.mjs` reads `process.env.SITE_URL`, falling back to a placeholder until a domain exists (see Commands above).
- **No client-side framework or bundler-managed JS.** Interactive behavior (hero slideshow, scroll parallax, mobile menu, product filtering, contact form, scroll-reveal, auth forms, cart) lives in plain vanilla JS files under `public/` (`hero-slideshow.js`, `parallax.js`, `mobile-menu.js`, `product-filter.js`, `contact-form.js`, `scroll-reveal.js`, `nav-auth.js`, `login-form.js`, `signup-form.js`, `account-page.js`, `cart.js`, `cart-page.js`, `product-detail.js`, `product-grid-cart.js`), each an IIFE, and is wired into pages via `<script src="..." is:inline>` tags rather than Astro component imports. Follow this pattern for new interactive widgets rather than introducing a UI framework.
- **Styling** is a single global stylesheet at `public/style.css`, linked from `BaseLayout.astro`. There are no CSS modules or scoped `<style>` blocks in use.
- **Photography** lives in `src/assets/images/` and goes through Astro's build-time image pipeline (resized, re-encoded to WebP) rather than being served verbatim from `public/`. `src/pages/index.astro` resolves it with an eager `import.meta.glob` over `*.{jpg,jpeg,png}` keyed by basename: `hero-1`–`hero-5` for the slideshow, `reason-1`–`reason-5` for the full-width rectangle banners in the Reasons section. Dropping a correctly-named file in replaces the CSS gradient placeholder without touching page code; a missing name keeps its gradient. A plain-English version for non-developers is in `HOW-TO.md`. Product photography (Loyverse-hosted, referenced by URL) renders via `background-size:contain` (not `cover`) so box art is never cropped.
